# 🚴 Loadline — 負荷のグラフに、その日の出来事を重ねる

## 1. サービス概要

**Strava の記録から日々の運動負荷とその推移を描き、そこに自分が書いた出来事のメモを重ねて読むための Web サービス。**

- **誰の**: Strava に数年分の記録が溜まっているが、年単位の振り返りができていない趣味のサイクリスト・ランナー
- **どんな課題を**: 負荷の推移をグラフにしても、**「なぜこの時期に落ちたのか」を後から思い出せない**。数値だけでは自分の生活と結びつかず、振り返りが「へえ」で終わってしまう
- **どう解決するか**: 日次負荷とその推移（エンジン・疲労・余力）のチャートに、**日付に紐づくメモをマーカーとして重ねる**。「3月の落ち込み＝出張が続いた時期」「6月の山＝200kmのロングライド」が、グラフの上で並んで見える状態をつくる。さらに、**その数値とメモの両方を LLM に読ませて振り返りの文章を生成する**

**本サービスは Strava の拡張サービスです。** Strava アカウントでログインし、Strava に既にある記録を読み込みます。新しく計測を始める必要はありません。

### 関連プロダクトとの関係

開発中の iOS アプリ **Cardilife** と同じ負荷モデル（エンジン・疲労・余力）を土台にしていますが、**リポジトリ・デプロイ・データベースを共有しない、完全に別のプロダクト**です。関係は次のとおりです。

| | Cardilife | Loadline（本サービス） |
|---|---|---|
| 何の拡張か | **HealthKit の拡張**（端末内のヘルスデータに解釈を足す） | **Strava の拡張**（クラウド上の記録に文脈を足す） |
| 構成 | 端末セントリック（算出も保存も端末内） | **サーバーセントリック**（算出も保存もサーバー） |
| 認証 | Firebase Auth（外部 OAuth を持たない） | **Strava OAuth**（連携が認証を兼ねる） |
| 時間の向き | 今日どうするか | **あの時期は何だったか** |
| 形態 | iOS アプリ | ブラウザ |

Cardilife では設計上の判断として算出も保存も端末側に寄せ、外部サービス連携を持たない構成にしました。**Loadline では逆に、サーバー側に寄せて外部サービス連携を中核に据えます。** 同じ負荷モデルを別の置き場所で組んだらどうなるかを試す2作目、という位置づけです（→ §10-2）。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

2026年7月、腰痛の治療のためにロードバイクを1ヶ月休みました。その後 Intervals.icu を開いたら、**VO2max が下がっていました。**

数値が下がったこと自体には納得しています。1ヶ月乗らなかったのだから当然です。**理由がはっきりしているので、落ち込みを見ても嫌な気持ちにはなりませんでした。**

引っかかったのは別のことでした。**グラフには「腰痛」と書かれていません。** そこにあるのは、ただ落ちた線だけです。今の私はその線を見て「腰痛の1ヶ月だ」と分かります。**では1年後の私は分かるだろうか、と考えて、たぶん分からないと思いました。**

思い返すと、覚えているライドは限られています。2026年4月にしまなみ海道を走ったことは覚えています。でもそれは、走ったこと自体が印象的だったからで、**記録を見て思い出したわけではありません**。逆に言えば、印象に残らなかった時期——調子が上がっていた月、落ちていた月——は、何があったのか既に思い出せません。

**数値の上下には必ず理由があります。** 腰痛、出張、天候、仕事の繁忙。理由があるからこそ数値が動いている。なのに、**グラフには理由のほうだけが残らない。** 数ヶ月経てば、残るのは「なんとなく落ちている時期」という形だけの記憶になります。

私のデータの流れは サイコン → Strava → Intervals.icu で、**Strava は中継地点として使っているだけ**、実際に眺めているのは Intervals.icu です。そこには日誌の欄もあります。でも書いたことがありませんでした。**書く場所が無かったのではなく、書いたものが後で目に入る形になっていなかった**からです。

---

### 2-2. なぜそれが「気になった」のか

50代後半という年齢が大きいと思います。

この年代になると、**練習が途切れることが日常的に起こります。** 腰痛のような故障、仕事の繁忙、家族の事情。20代なら「たまたま休んだ週」で済むものが、1ヶ月単位の中断になります。そして回復にも時間がかかるため、**中断の影響が数値にはっきり出ます。**

つまり私のグラフは、若い人のグラフより凹凸が激しい。**そしてその凹凸のほとんどは、トレーニングの内容ではなく生活の側に理由があります。** だからこそ、生活の側の事情を書き残しておかないと、後から読めるものになりません。

もう一つは、データを揃えることに手間をかけてきた経験です。サイコンから Strava、Strava から Intervals.icu へと連携を通すのに何日も費やしたことがあります。**そこまでして揃えたデータを、結局は眺めるだけで終わっている**という感覚がありました。数値は溜まっている。溜まっているのに、読めていない。

そして「読めない」の正体が、**数値そのものではなく文脈が無いことだ**と気づいたのが、7月の腰痛のときでした。落ちた線に理由が添えられていれば、それは記録として読めます。添えられていなければ、ただの形です。

**「グラフの隣にメモがある」ではなく「グラフの上にメモが乗っている」**——この形にすれば、読み返す動機と書く動機が同時に生まれるのではないか、と考えました。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

過去の記録をグラフにしても、**そのグラフの上下が何によるものだったか思い出せない**。

---

### 3-2. 本当に解決したい課題は何か

- **なぜそれが困る？** → グラフが「数字の上下」のままで、自分の生活と結びつかないから
- **なぜそれが困る？** → 結びつかないと、振り返りが「ふーん」で終わり、次の判断にも記憶にも残らないから
- **なぜそれが困る？** → 残らないと、**記録を取り続ける理由が薄れる**。何のために溜めているのか分からなくなり、やがて記録すること自体をやめてしまうから

→ **本当に解決したい課題:**
> **記録を続けているのに、後から自分の言葉で読み返せる形になっていないために、蓄積が意味を持たず、続ける動機そのものが失われていくこと。**

「グラフを描くアプリが欲しい」は手段です。解きたいのは、**続けた事実が本人の中に残らない**という、記憶と継続の問題です。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**「50代後半の会社員男性。ロードバイクとランニングを続けており、サイコン → Strava → Intervals.icu という流れでデータを揃えている。Strava は中継地点として使うだけで、実際に眺めているのは Intervals.icu。故障や仕事の都合で、年に何度か1ヶ月単位で乗れない時期がある。数値が落ちれば理由は分かるが、数ヶ月経つと『この時期は何だったか』が思い出せない。日誌の欄があることは知っているが、書いたことはない。」**

#### 年齢設定
- **年齢**: **40〜60代**（想定の中心は50代）
- **理由**: この年代は、**記録の蓄積年数がある**（Strava を数年使っている層が多い）一方で、**生活のイベントによって練習が途切れる頻度が高い**。出張、家族の事情、故障、体調不良——20〜30代なら「たまたま休んだ」で済むものが、この年代では数週間から数ヶ月の中断になります。つまり**グラフに大きな凹凸が生まれやすく、その理由が生活側にある**年代です。凹凸が少なく毎週同じように走れている人にとっては、メモを重ねる価値がそもそも生まれません。

#### 生活・状況設定
- **生活・状況**: 平日はデスクワーク。週末を中心に乗り、月に1〜2回は長めのライドやイベントに出る。仕事や家庭の都合で乗れない週が定期的に発生する。
- **理由**: **乗れない週があること自体が、このサービスの価値の源泉**です。切れ目なく走れている人のグラフは平坦で、読み解く必要がありません。「なぜここで途切れたか」が生活側の事情である人ほど、その事情を書き残す意味があります。アプリを使うことで、**中断の理由が記録として残り、後から見たときに「サボった谷」ではなく「出張の谷」として読める**ようになります。

#### 環境設定
- **環境**: **Strava に記録が既にある人**。PC またはスマートフォンのブラウザで利用（ネイティブアプリではない）。
- **理由**: この環境特有のハードルは「**データは揃っているのに、それを振り返る場所がない**」ことです。新しく計測機器を買う必要も、記録の取り方を変える必要もありません。既にある Strava のデータを読み込み、**そこに欠けている「文脈」を足すだけ**で課題が解けます。またブラウザで完結させることで、アプリのインストールという最初のハードルを外しています。

---

### 4-2. 自分とユーザーの距離

→ **自分自身**

理由: 上記のペルソナは現在の自分に近いものです。Strava に記録があり、振り返れていない状態も、練習日誌が続かなかった経験もそのままです。**作った初日から自分のデータで使える**ため、想像で仕様を決める部分が少なく、使われない機能を作り込むリスクを抑えられると考えています。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **最初に使ってくれそうな人**: 自分。次に、一緒に走っている自転車仲間（50代前後が中心）。
- **その人はどんな場面で思い出すか**: 長めのライドから帰った日の夜、イベントやレースに出た直後、月が変わったタイミング、そして「最近調子が悪い気がする」と感じたとき。
- **今の生活の中で、代わりに使っているものは何か**:
  - **Intervals.icu**（数値は十分すぎるほど見られるが、日誌欄がカレンダー側にあり、チャートを見ながら読めない）
  - Strava のアクティビティ名・説明欄（書ける場所はあるが、**アクティビティが無い日には何も書けない**。そもそも中継地点として使っているので開かない）
  - 手帳・メモアプリ（グラフと切り離されているため読み返さない）
  - そして**自分の記憶**（数ヶ月で消える）
- **置き換えてまで使う理由**: 上記のどれも「グラフと出来事が同じ場所にない」という点で共通しています。**書く場所と読む場所が一致していること**が、置き換えの理由になると考えています。

※ このあたりは推測が含まれるため、着手後に自転車仲間数名にヒアリングして検証する予定です。

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

**知る・思い出すきっかけ**

「Strava 振り返り」「トレーニング 日誌 続かない」「ロードバイク 練習 記録」といった検索からの流入と、自転車コミュニティ（Strava クラブ、X）での紹介を想定しています。原体験と、実際に自分のデータで数ヶ月使った結果を記事として公開する予定です。

**最初の一歩（登録・導入）**

1. 「Strava で連携」ボタンを押す（**アカウント登録はこれだけ**。メールアドレスもパスワードも入力しません）
2. 設定画面で最大心拍・安静時心拍を入力する
3. 同期ボタンを押す

ここまで**3分以内**で、**過去のアクティビティが取り込まれ、その場で数ヶ月分のチャートが描かれる**ことを最優先の体験とします。Strava には過去データが既に溜まっているため、**初日から「去年の春の山と谷」が目の前に出る**——これが最初の発見になります。そして**その谷にメモが1つも無いことに気づく**ところから、書く行動が始まると考えています。

**利用を続ける理由**

- **書けば書くほど、次に振り返るときの解像度が上がる**。やめる＝これまで書いた文脈を捨てることになる
- メモを書く動機が**グラフから生まれる**（谷や山が目に入ることが、そこに何かを書くきっかけになる）
- 1日1行、乗った日だけでよく、**書かなくてもチャートは動く**。書かない期間があっても復帰できるため、日誌のように「途切れたら終わり」にならない

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

Strava には**それ自体を拡張するサービス群**が既に存在します（Strava OAuth でログインし、Strava が持っていない切り口を足すタイプ）。Loadline はこのジャンルに属します。したがって比較対象は Strava 本体ではなく、**Strava の周辺に何があり、そこに何が無いか**です。

| サービス名 | URL | どんなことができるか | 足りないこと |
|---|---|---|---|
| **Intervals.icu**（★最も意識する競合。Strava 拡張） | https://intervals.icu | Strava と連携し、負荷の蓄積と疲労を指数加重移動平均で可視化。パワー分析、ゾーン分布、カレンダー。基本無料 | **機能が多く、指標の数も多い**ため、日常的に眺めるには負担が大きい。日誌欄はあるが**チャートとは別のカレンダー上にあり**、グラフを見ながら読むことができない。設定項目が多く、導入のハードルが高い |
| **Strava**（拡張元） | https://www.strava.com | ライド・ランのログ、GPS・心拍の記録、アクティビティごとの説明欄、年間サマリ | **アクティビティ単位でしか書けない**（乗らなかった日・休んだ日に何も残せない）。負荷の長期的な推移の表示は有料機能で、しかも記述と並べて見られない。SNS的な性格が強く、他人に見せる前提の場所に「体調を崩した」とは書きにくい |
| **TrainingPeaks** | https://www.trainingpeaks.com | 負荷管理と計画作成の定番。コーチとの共有機能 | 競技志向のアスリートとコーチ向けで**多機能かつ有料**。趣味で乗る層にとっては過剰 |
| **VeloViewer / Elevate**（同ジャンル） | https://veloviewer.com | 同じく Strava 拡張。走行実績の集計・可視化、セグメントやヒートマップなど**「走った事実」の見せ方**を競う | いずれも**数値をどう見せるか**の勝負で、**ユーザーが書いた言葉を扱わない** |
| **Day One / 手帳などの日記アプリ** | https://dayoneapp.com | 日付ごとに自由に書ける。写真も残せる | **数値と結びつかない**。書いた内容を「あの落ち込みの時期」から辿ることができず、時系列を延々スクロールするしかない |

### 5-2. それでも自分が作りたい理由

最初に感じた不満は、**Intervals.icu は指標が多すぎる**ということでした。並んでいる数値のどれを見ればいいのか分からず、結果としてどれも見なくなる。私が知りたいのは「積み上がっているか」「疲れているか」「余裕があるか」の3つだけでした。

**ただし、ここで「機能を減らした版を作る」と考えるのは間違いだと思っています。** 機能の数は症状であって原因ではないからです。

本当の原因は、**書いた場所と見る場所が違う**ことでした。Intervals.icu にもメモを書く欄はあります（あるのです）。しかしそれはカレンダー側にあり、チャートを見て「この谷は何だったか」と思ったときには、カレンダーに移動して該当月まで戻り、日付を探す必要がある。**この数手間があるだけで、私は調べるのをやめてしまいます。** 機能をいくら減らしても、この構造は直りません。

日記アプリの側にも、同じ問題が逆向きに現れます。書くことはできても、**書いたものを呼び出す入口が「日付」しかない**。人間は日付を覚えていません。覚えているのは「調子が良かった時期」「落ちていた時期」という**波の形**のほうです。

つまり不満は「機能が多い／少ない」ではなく、**グラフと言葉が別々の場所に置かれていること**そのものにあります。画面が3つしかないのは、削った結果ではなく、**この一点に絞った結果**です。

### 5-3. 差別化を「体験価値」で表現する

- **私のアプリの差別化ポイント**:
  **数年分の記録が溜まっているサイクリストが、半年前の落ち込みを見て「ああ、あの出張の時期か」と一瞬で思い出せる。**

グラフの谷をクリックすればその日のメモが開き、メモを書きたくなれば同じ画面から書ける。**思い出す入口が「日付」ではなく「波の形」になっている**ことが、このサービスの体験上の中心です。

また、**メモをアクティビティに紐づけず日付だけで持つ**という設計上の判断も、体験に直結しています。休養した日、旅行していた日、故障していた日——**アクティビティが存在しない日こそ書き残す価値がある**ためです。Strava の説明欄では原理的に書けない部分がここにあたります。

そしてもう一つ、**LLM に数値とメモの両方を読ませて振り返りを書かせる**ことも差別化の一部です。

> 「この3ヶ月、負荷は2月に一度落ちています。同じ時期のメモに『出張』が3回。3月に戻したあと、4月の『ロングライド 200km』でエンジンが最高値になりました。5月以降メモが途切れていますが、負荷も同時に落ちています。」

測定値メモ（VO2max）を入力していれば、それも同じ入力に含まれます——「3月に VO2max 46、6月に 48。その間のメモに『ロングライド』が4回」といった形です。

数値だけを渡して「エンジンが上がっています」と言わせるなら、どのサービスにもできます。**Loadline だけが持っている入力は、ユーザーが書いた自然言語のメモ**です。構造化されていないテキストと数値を突き合わせるのは、まさに LLM が要るタスクであり、**このサービスがメモを持っているからこそ成立する機能**です。

Strava 拡張サービス群は「走った事実をどう見せるか」を競っています。Loadline は**「本人が書いた言葉と、そこから読める話」**を扱う、という点で土俵が違います。真面目な分析ツールとして Intervals.icu と競うのではなく、**自分の記録を読み返して面白い場所**を目指します。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化**: 乗った日に1行書くようになる。長めのライドや、逆に乗れなかった週にこそ書き残すようになる
- **気持ちの変化**: グラフが「他人が作った統計」ではなく「**自分の記録**」として読めるようになる。乗れなかった時期を「サボった谷」ではなく「出張の谷」として受け止められる
- **考え方の変化**: 数値の良し悪しではなく、**そこに至った経緯**で自分の状態を捉えるようになる。LLM が読み上げる振り返りによって、自分では気づいていなかった規則性に出会う

### 6-2. 価値を一文で表す

**このサービスは、記録は続けているのに振り返れていない人が、数値と出来事を同じグラフの上で並べて、自分の記録として読み返せるようになるサービスです。**

## 7. このアプリで実現すること

### MVPで作る機能

| # | 機能 | 内容 |
|---|---|---|
| 1 | Strava OAuth 連携 | ログインを兼ねる。メール／パスワードによる登録は持たない |
| 2 | アクティビティの取り込み | 手動の同期ボタン。前回同期以降の差分のみ取得 |
| 3 | 設定 | 最大心拍・安静時心拍の入力 |
| 4 | 日次負荷の算出 | アクティビティのサマリ値から算出。同日複数は合計 |
| 5 | 推移の算出 | エンジン・疲労・余力 |
| 6 | チャート表示 | 日次負荷の棒グラフ＋3本の線。期間切り替え（1ヶ月／3ヶ月／6ヶ月） |
| 7 | イベントメモ | 登録・編集・削除。日付に紐づけて保持し、チャート上にマーカーとして重ねる |
| 7b | **測定値メモ（VO2max）** | メモの一種として数値を記録できるようにする。チャートに点で重ねる（→ §12） |
| 8 | アクティビティ一覧 | 各行から Strava の該当アクティビティへ遷移 |

### チャレンジ枠：LLM による振り返りの生成

**受講コース（Python / AI）の中心にある技術を、この企画で最も活きる形で使う挑戦です。**

| # | 機能 | 内容 |
|---|---|---|
| 9 | **LLM による振り返りの生成** | 指定期間の**日次負荷・エンジン・疲労・余力の系列**と、**同じ期間にユーザーが書いたメモ**の両方をモデルに渡し、振り返りの文章を生成する。数値の増減とメモの内容を突き合わせ、「いつ何があって、そのあとどうなったか」を文章にする |

**設計上の要点**

- **入力にメモを含めることが必須**です。数値だけを渡すなら、このサービスである必要がありません（→ §5-3）
- **断定的な指示は出しません**が、**指摘はします**。「休むべき」ではなく「5月以降メモが途切れていますが、負荷も同時に落ちています」という書き方です。医学的・医療的な助言は行いません（→ 懸念点⑥）
- 生成はユーザーが明示的にボタンを押したときだけ行い、自動では走らせません（コストとレート制限の管理のため）

**MVP に含めるか、本リリースに回すかは未定です。** コア機能（連携・チャート・メモ）が動いたあとに着手し、期間内に収まらなければ本リリースへ送る前提で進めます。**モデルは Google 系（Vertex AI / Gemini 系）を想定していますが、選定は着手時に行います**（→ §10-2）。

### 本リリースで作る機能

| # | 機能 | 内容 |
|---|---|---|
| 10 | Webhook による自動同期 | Strava の Webhook を受け、同期ボタンを押さなくても取り込まれる |
| 10b | **タニタ Health Planet 連携（体重のみ）** | 体組成計の**体重だけ**を OAuth 経由で取り込み、測定値メモとして自動登録する。体脂肪率・筋肉量などは取り込まない。**API の利用登録ができなければ実装しない**（→ §12） |
| 11 | メモの検索・一覧 | 書いた内容から辿る導線。チャートからの導線と両方向にする |

## 8. このアプリの懸念点とその対策

### 懸念点① メモが書かれず、ただのグラフ表示ツールになる

- **何が問題になりそうか**: このサービスの価値は「メモが重なっていること」に依存しています。**メモがゼロなら、Intervals.icu の劣化版にしかなりません。** そして私自身、練習日誌を2回続けられなかった前科があります
- **なぜそう思うか**: 「書く」という行動は、書いた時点では見返りがありません。見返りが出るのは数ヶ月後です。この時間差が、あらゆる日誌ツールが続かない理由だと考えています
- **考えている対策**:
  - **書く場所を、読む場所と同じにする**。チャートの日付をクリックすればその場で書ける形にし、「日誌を開く」という別の行動を発生させない
  - **1日1行でよい**ことを入力欄の初期状態で示す（タイトルのみで保存できる設計にし、本文は任意）
  - **書かなくてもチャートは完全に動く**設計にすることで、「書けなかった期間があるから終わり」にしない
  - 「負荷が高い日／大きく落ち込んだ日にメモが無い」ことを画面上でそっと示す導線を検討する（ただし**通知や催促にはしない**——作り込みすぎると MVP を超えるうえ、義務感は継続を壊すため）

### 懸念点② データ源が Strava 1本であることへの依存

- **何が問題になりそうか**: Strava の API 仕様変更や利用条件の変更で、サービスが成立しなくなる可能性があります。実際に Strava は過去にエンドポイントの廃止やレート制限の変更を行っています
- **なぜそう思うか**: 外部 API は壊れる前提で考える必要があります。代替として検討した Google Fit REST API は 2024年5月から新規登録を受け付けておらず、その後継にあたる API も移行期にあたるため、**現時点で Strava 以外に現実的な選択肢がない**というのが実情です
- **考えている対策**:
  - Strava への呼び出しを**バックエンドの1モジュールに完全に閉じ込める**。データ源が増えたり替わったりしても、影響範囲を取り込み処理だけに限定する
  - 取り込んだアクティビティは**自前の DB に保存する**（毎回 Strava に問い合わせる作りにしない）。連携が切れても、過去の記録とメモは残り、チャートも描ける
  - **ユーザーが書いたメモは Strava に一切依存しません。** 最悪の場合でも、このサービスの独自資産であるメモは失われません

### 懸念点③ 「余力」が、長期休養明けに逆の印象を与える

- **何が問題になりそうか**: 指数移動平均の構造上、**長期間休むと疲労のほうが先に下がる**ため、余力が大きなプラスを示します。実際には体力が落ちているのに、グラフの上では「余裕がある」ように見えてしまいます。故障明けという、最も慎重であるべき局面で起きる誤読です
- **なぜそう思うか**: この弱点は移動平均を使う負荷モデルに共通するもので、既に知られています
- **考えている対策**:
  - **これこそがメモの出番**です。2026年7月に腰痛で1ヶ月休んだ実データが手元にあるので、これで検証できます。「腰痛で休養」というメモがその期間に乗っていれば、余力が跳ねている理由をユーザー自身が読み取れます。**この懸念は、このサービスの中心的な価値によって緩和される**という関係にあります
  - **画面上でも「休養明けは余力が実態より高く出る」ことを注記します。** LLM による振り返りにも、この性質をあらかじめ伝えておき、余力の高さだけを根拠に前向きな評価をさせません
  - 時定数（42日／7日）が**暫定値**であることをコード上・ドキュメント上に明記し、実データで検証する

### 懸念点④ 最大心拍・安静時心拍の手入力が、導入の壁になる

- **何が問題になりそうか**: 連携直後に数値の入力を求められると、「自分の最大心拍を知らない」ユーザーはそこで離脱します
- **なぜそう思うか**: 心拍計を使っていても、最大心拍を正確に把握している人は多くありません
- **考えている対策**:
  - **年齢からの推定式（220 − 年齢）は使いません。** この式は年齢が上がるほど実測から外れ、閾値が下振れして強度を過大に評価するため、想定ユーザーである50代以上で最も当てになりません
  - 代わりに、**取り込んだアクティビティの最大心拍の観測値を初期値として提示する**方向で検討します（実際に出た値のほうが推定式より確かなため）
  - 心拍データが無いアクティビティは負荷を算出せず、**欠測として扱って埋めない**方針とします

### 懸念点⑤ 他社の商標・造語との衝突

- **何が問題になりそうか**: 負荷管理の分野には、特定のサービスの商標や造語として定着している用語があります。これらを画面や変数名に使うと、法的な問題に加えて「模倣」と受け取られます
- **考えている対策**: 計算モデルは**公知の学術手法（Banister の TRIMP）のみ**を使用し、他社の商標・造語は変数名・UI 文言・コメントのいずれにも使いません。指標名は **エンジン / 疲労 / 余力（Engine / Fatigue / Headroom）** とし、**判定を含む語や、他の意味と衝突する語も避けます**。この方針は README に留めず、**禁止語を検出するチェックを CI に組み込んで機械的に守ります**

### 懸念点⑥ LLM が、もっともらしい嘘を書く／踏み込みすぎる

- **何が問題になりそうか**: 生成された振り返りが、**実際のデータに無いことを書く**可能性があります。「4月は調子が良かったようです」と書かれても、その根拠がデータにあるのか分かりません。もう一つは逆方向で、**医学的な助言に踏み込んでしまう**リスクです（「オーバートレーニングの可能性があります」「休養を取るべきです」）
- **なぜそう思うか**: 生成モデルの一般的な性質です。特に数値の系列を渡した場合、増減の向きや時期を取り違えたまま自然な文章にしてしまうことがあります
- **考えている対策**:
  - **モデルに渡す数値を、あらかじめ集計した確定値に絞る**。生の系列を長々と渡して読ませるのではなく、「期間内の最大・最小とその日付」「前期間との比較」「メモの一覧」といった**すでに計算済みの事実**を構造化して渡し、モデルの仕事を「並べ替えて文章にすること」に限定します
  - **生成文の隣に、根拠となったチャートを必ず並べて表示する**。文章だけを単体で見せない
  - **医療・診断の領域には踏み込まない旨をシステムプロンプトで明示**し、UI 上にも「これは医学的な助言ではありません」と表示します。トレーニングメニューの自動生成もスコープ外とします（→ §7）
  - **生成はユーザーが押したときだけ**にし、自動生成による誤情報の垂れ流しを構造的に防ぎます

### 懸念点⑦ LLM の利用コストと、外部 API 依存の増加

- **何が問題になりそうか**: 無料公開する個人サービスに従量課金の API を組み込むと、**想定外の利用でコストが膨らむ**可能性があります。また外部依存が Strava に加えてもう1つ増えます
- **考えている対策**:
  - 生成を**手動トリガーのみ**とし、**ユーザーあたりの実行回数に上限**を設ける
  - 渡す入力を集計済みの確定値に絞ることで、1回あたりのトークン量を小さく保つ（上記⑥の対策と同じ設計が、そのままコスト対策になります）
  - **LLM を呼ぶ処理を1つのモジュールに閉じ込め、停止してもサービスの他の機能が動く**構造にします。チャートもメモも LLM に依存しません

## 9. 今後の展開・発展の方向性

### ユーザーはなぜ使い続ける？

書いたメモは**時間が経つほど価値が上がる**性質を持っています。1ヶ月分のメモにはほとんど意味がありませんが、2年分溜まると「毎年6月に落ちている」「調子が良い時期の前には必ず長距離を踏んでいる」といった、自分でも気づいていなかった規則性が見えてきます。**やめる＝この蓄積を捨てること**になるため、続けるほどやめにくくなります。

### データが溜まると何ができる？

- **年ごとの重ね合わせ**: 今年と去年の同じ時期を並べて表示する
- **メモと数値の関連の提示**: 「『レース』とメモした日の前後2週間」のような切り口での抽出
- **LLM による振り返りの深化**: 期間を年単位に広げ、複数年を横断した振り返りを生成する
- **書いた言葉の傾向**: どんな出来事を書き残しているかそのものが、その人の関心の記録になる

### 他の人と関わる余地はある？

MVP では**完全に個人利用**とします（Strava の利用規約上も、他人のデータを見せる作りは不可）。ただし将来的には、**特定の期間のチャートを読み取り専用の URL で共有する**（イベントに向けた数ヶ月の経過を仲間に見せる、など）という方向は考えられます。SNS 化はしません——「体調を崩した」と書ける場所であることが、このサービスの前提だからです。

### 今考えている発展案

- **機能追加の方向性**: Webhook による自動同期、年次の振り返りビュー、メモへの写真添付、LLM による振り返りの深化
- **関連プロダクトへの導線**: 本サービスはブラウザで開けるため、iOS アプリより入口が広くなります。負荷の推移という考え方に触れた人が、睡眠中の心拍まで含めてより深くやりたくなったときの行き先として、Cardilife を案内できます（→ §1）
- **UI・体験の改善**: メモが無い谷・山への気づきの導線、モバイルでの入力のしやすさ
- **機能以外の工夫**: 自分自身が数ヶ月使い続け、実際に溜まったチャートを公開する。**「作った人が使い続けている」ことが、この種のツールでは最も強い説得力を持つ**と考えています

### 10-2. 技術選定の比較検討

#### バックエンドのフレームワーク

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **FastAPI** | **採用** | 受講している Python/AI コースの卒業要件を満たす。非同期の外部 API 呼び出し（Strava）と相性が良く、Pydantic による入出力の型定義がそのまま API ドキュメントになる |
| Django REST Framework | 不採用 | 管理画面や認証など、今回使わない機能が多い。**このサービスは管理者が触る画面を持たない** |
| Flask | 不採用 | 軽量だが、非同期処理・型・バリデーションを自前で組む必要があり、FastAPI を選ばない理由がない |

#### データベース

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **Neon** | **採用** | スケールトゥゼロを維持しており、アクセスが無い期間の課金が発生しない。無料枠がアクセス頻度によって一時停止しない。SQLAlchemy + Alembic をそのまま使える |
| Supabase | 不採用 | 無料枠は**7日間アクティビティが無いとプロジェクトが一時停止**する。個人利用中心で、日に数回しか触られないこのサービスとは相性が悪い |
| Cloud SQL | 不採用 | GCP ネイティブの利点はあるが、**常時起動インスタンスの課金**が個人開発のコストに見合わない |
| Cloudflare D1 | 不採用 | 下記「ホスティング」の検討に連動して不採用 |

> **Neon の既知のトレードオフ**: 日本リージョンが無く、最寄りはシンガポール（+80〜100ms 程度）。個人の記録量では体感差にならないと判断しています。問題化した場合の切り戻し先として Cloud SQL 東京リージョンを想定します。

#### API のホスティング

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **Cloud Run**（min-instances=0） | **採用** | リクエストが無い間は課金されない。コンテナで動くため、ライブラリの制約が無い |
| **Cloudflare Workers（Python）** | **不採用（2026-09-09 判断）** | Python Workers は Pyodide / WebAssembly 上で動くため、**asyncpg や psycopg のようなバイナリドライバが使えず、TCP 接続も直接張れない**。D1 か Neon の HTTP エンドポイントに生 SQL を投げる形になり、**SQLAlchemy と Alembic を捨てることになる**。FastAPI 自体は ASGI 対応なので「動かない」わけではなく、詰まるのは DB 接続の部分です。卒業制作の成果物として、ORM とマイグレーションを失う代償が大きすぎると判断しました |
| Fly.io / Render | 不採用 | 選択肢としては成立するが、Cloud Run に運用経験があり、Secret Manager との統合も含めて手戻りが少ない |

#### チャート描画ライブラリ

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **Apache ECharts** | **採用** | このサービスの中核は「**棒グラフ＋複数の折れ線＋任意の日付に立てるマーカー**」を1つのチャートに同居させることです。ECharts は `markPoint` / `markLine` を標準で持ち、クリックイベントから日付を取得する処理も素直に書けます。期間切り替え・ツールチップも設定だけで済みます |
| Recharts | 不採用 | React との親和性は高いが、**任意の日付に立てるマーカーとそのクリック処理を自前で組む必要がある**。最も工数の読めない部分が自前実装になる |
| Chart.js | 不採用 | 同上。加えてアノテーション表示はプラグイン依存になる |
| D3.js | 不採用 | 表現の自由度は最も高いが、**軸・凡例・ツールチップまで自前**になり、期間内に収まるか読めない |

#### フロントエンドのフレームワーク

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **React（Vite）** | **採用** | **Web の React に実務経験があり**、キャッチアップの時間を要しない。求人・情報量ともに最も厚い |
| Vue | 不採用 | 学習コストは低いが、就職を見据えると React のほうが選択肢が広い |
| Next.js | 不採用 | **SSR も SEO も必要としない**（ログイン後にしか見る画面がない）ため、SPA で足りる。フレームワークの学習が本題から外れる |

#### 認証

| 候補 | 採用/不採用 | 理由 |
|---|---|---|
| **Strava OAuth 単独** | **採用** | **Strava 連携が認証を兼ねます。** `strava_athlete_id` がそのまま一意のユーザー識別子になるため、別の認証基盤を足す必然性がありません。ユーザーはボタン1つでログインでき、メールアドレスもパスワードも入力しません（→ §4-4） |
| Firebase Auth を併用 | 不採用 | Cardilife で使用しており実装経験はありますが、**ここでは害のほうが大きい**と判断しました。①ログインが「Google でサインイン → その後 Strava を連携」の2段階になり、導入の軽さという最大の利点が消える ②本サービスは Strava ユーザーしか対象にしないため、複数のログイン手段が要らない ③別プロダクトである Cardilife とアカウントを共有する予定がないため、認証基盤を揃える実利がない。**そして、外部 OAuth の実装そのものが今回の学習目的です**（下記「チャレンジしたい点」） |

> Cardilife が Firebase Auth を選んだのは、**外部 OAuth を1つも持たないプロダクトだから**認証を別途用意する必要があったためです。Loadline は外部 OAuth が中核にあり、前提が逆になっています。

#### SPA の配置とセッション

この2つは独立した論点ではないため、まとめて判断しました。

| 構成 | 採用/不採用 | 理由 |
|---|---|---|
| **SPA を Cloud Run に同居 ＋ httpOnly Cookie** | **採用** | API と同一オリジンになるため、**CORS の設定が不要**で、Cookie も `SameSite=Lax` で素直に動きます。トークンを JavaScript から読めない位置に置けるため、XSS でセッションを奪われません |
| SPA を Cloudflare Pages に分離 | 不採用 | 別オリジンになるため、Cookie を使うなら `SameSite=None; Secure` と CORS の資格情報設定が必要になり、ブラウザのサードパーティ Cookie 規制の影響も受けます。静的配信としては優れていますが、**セッション管理の面倒がそれを上回る**と判断しました |
| JWT を localStorage に保持 | 不採用 | XSS でトークンを読み出されるリスクがあり、個人の健康関連データを扱う以上避けたい |

#### LLM の呼び先

**着手時に決定します。** 現時点では次の条件で選定する予定です。

- **Google 系（Vertex AI / Gemini 系）を第一候補**とする。バックエンドが Cloud Run 上にあるため、認証（ADC）と秘匿情報の管理を GCP に統一でき、Secret Manager をそのまま使える
- 渡す入力を集計済みの確定値に絞る設計（→ 懸念点⑥）のため、**大きな入力を扱えることよりも、短い日本語の生成が安定していることと、単価の低さ**を優先する
- **モデル名を README に固定しません。** 選定時点で利用可能なモデルの中から、上記の条件で選びます

#### 外部サービス連携の置き方

**Strava API の呼び出しを、バックエンドの1モジュールに閉じ込めます**（→ 懸念点②）。これは障害対策であると同時に、**連携先を増やせる形にしておく**という意図もあります。

本リリースで予定しているタニタ Health Planet 連携（→ §7）は、**2つ目の外部 OAuth**になります。1つ目で作った「認可 → トークンの暗号化保存 → リフレッシュ → 差分取得」という流れが、2つ目で本当に再利用できる形になっているかが、設計の答え合わせになります。**外部連携を中核に据えたサーバーセントリック構成である以上、ここが最も学びのある部分**だと考えています。

#### 今回チャレンジしたい点

- **OAuth 2.0 の実装**（認可コードフロー、トークンのリフレッシュ、暗号化した保存）。既存の認証サービスに頼らず、外部サービスとの連携を自分で組む経験を得たい
- **算出ロジックを純粋関数として切り出し、テストで守る**こと。TRIMP と指数移動平均の計算は、DB にも HTTP にも依存しない層に置き、既知の入力に対する期待値をテストで固定します
- **LLM を、必然性のある形で組み込む**こと。受講コースの中心にある技術ですが、「使うために使う」形にはしたくありません。**数値とユーザーが書いた自然言語の両方を入力にできるのは、このサービスがメモを持っているからこそ**です。加えて、もっともらしい嘘を書かせないための入力設計（集計済みの確定値だけを渡す）と、踏み込ませないための制約は、**LLM を実務で使ううえで避けて通れない部分**なので、ここに取り組みます（→ §7 チャレンジ枠・懸念点⑥）

#### 不安な点

- **Strava API の実際の挙動**（レート制限の運用、差分取得の指定、心拍が入っていないアクティビティの扱い）。ドキュメントを読むだけでは分からない部分があるため、**着手直後に最小構成で疎通を確認します**
- **ECharts でのマーカー操作**（メモが同じ日に複数ある場合の表示、クリック位置から日付を取る処理）
- **LLM に渡すデータの整形と、出力の安定性**。どこまで集計してから渡せば嘘を書かなくなるかは、実際に試さないと分かりません

### 10-3. キャッチアップ不足の懸念

**現状の習熟度**

- **React（Web）／ Vite**: **実務経験があります。** キャッチアップの時間を見込む必要はありません
- **FastAPI / SQLAlchemy / Cloud Run / Neon**: Cardilife のバックエンドで使用しており、一定の実績があります。**この構成を選んだ理由の一つが、そこにキャッチアップの時間を使わずに済むこと**です
- **ECharts**: Cardilife で WebView 経由で使用した経験があります
- **Strava API**: **未経験です**
- **LLM API の組み込み**: **未経験です**

**懸念と、それに対する進め方**

**技術構成の大半を、既に実務または個人開発で触れたもので固めました。** これは意図的な選定です。卒業制作の期間内に新しい技術のキャッチアップと企画の実現を同時に進めるのは危険で、**時間を使うべきなのは「動かしたことがない部分」だけ**だと考えています。

その結果、未経験の領域は **「Strava API」と「LLM API の組み込み」の2つ**に絞られました。この2つの技術検証を最初のイシューに置きます。

1. **着手後の最初の1〜2週間**: Strava の OAuth を通してアクティビティを1件取得し、ブラウザに表示するところまでを通す。ここが通れば、コア機能は既に経験のある技術の組み合わせになります
2. **コア機能が動いた後**: LLM の組み込みに着手する。ここが期間内に収まらなければ、本リリースへ送る判断をします（→ §7 チャレンジ枠）

**未経験の部分を前後の両端に置き、間を経験済みの技術で埋める**構成にすることで、期間内に収まらないと分かった場合に、削る判断を早い段階で下せるようにしています。

## 11. 算出方法（参考）

### 日次負荷

心拍の時系列データ（Strava の streams API）は取得せず、**アクティビティのサマリ値のみ**で完結させます。平均心拍1つから算出できる Banister の TRIMP を使用します。

```
HRr   = (平均心拍 − 安静時心拍) / (最大心拍 − 安静時心拍)
TRIMP = 運動時間(分) × HRr × 0.64 × e^(1.92 × HRr)
```

同じ日に複数のアクティビティがあれば合計し、アクティビティの無い日は 0 とします。

### 推移

| 指標 | 英語名 | 定義 |
|---|---|---|
| **エンジン** | `Engine` | 日次負荷の 42 日 指数移動平均 |
| **疲労** | `Fatigue` | 日次負荷の 7 日 指数移動平均 |
| **余力** | `Headroom` | エンジン − 疲労 |

**時定数（42 / 7）は暫定値です。** コード上の1箇所に定数としてまとめ、暫定である旨を明記します。

### この3つの指標は独自のものではありません

**エンジン・疲労・余力という構成（長い時定数の移動平均 − 短い時定数の移動平均）は、負荷管理の分野で広く使われている公知の組み合わせです。** Intervals.icu をはじめとする既存サービスと同じ骨格であり、式の系統まで独自にしたわけではありません。避けているのは他社の商標・造語と視覚表現であって、手法そのものではありません（→ 懸念点⑤）。

**このサービスの独自性は算出方法ではなく、その線の上にユーザーの言葉を重ねることにあります。**

### 出典

- **重み係数（0.64 / 1.92）**: Banister, E.W. (1991) "Modeling elite athletic performance", *Physiological Testing of the High-Performance Athlete*, 2nd ed., Human Kinetics, pp. 403–424. 査読誌では Morton, Fitz-Clarke & Banister (1990) *J Appl Physiol* 69(3):1171–1177 が同じ重みを使用しています
- **2成分モデル（長い成分 − 短い成分）**: Banister, Calvert, Savage & Bach (1975) *Aust J Sports Med* 7(3):57–61
- **時定数 42日 / 7日**: 論文が指定した値ではなく、この分野で慣用的に使われている値です。**本サービスでは暫定値として扱います**

### 既知の簡略化

- **平均心拍1つで1回分の負荷を算出します。** 本来の TRIMP は心拍の時系列に対して1分ごとに重みを掛けて合計するもので、**平均心拍による算出は近似**です。強度の起伏が大きいアクティビティ（インターバル走など）では、実際より軽く見積もられます。心拍の時系列を取得しない方針とのトレードオフとして受け入れます
- **種目による心拍特性の差を考慮しません。** 一般に自転車の閾値心拍はランニングより10〜15bpm 低いことが知られていますが、本サービスでは最大心拍・安静時心拍を種目共通の1組で保持します。**同一ユーザーの推移を追うことが目的**であり、種目間の絶対値の比較を行わないため、MVP では許容します
- **心拍データが無いアクティビティは、負荷を算出せず欠測として扱います**（0 で埋めません）

## 12. データモデル（素案）

DB は常に SI 単位で保存し（kg, km, ms, bpm）、単位変換は表示側で行います。分類値は言語に依存しない enum コード（`bike`, `run`, `walk`）で保持します。

| テーブル | 主な列 |
|---|---|
| `users` | id, strava_athlete_id, 表示名, created_at |
| `oauth_tokens` | user_id, access_token（暗号化）, refresh_token（暗号化）, expires_at |
| `user_settings` | user_id, hr_max, hr_rest |
| `activities` | id, user_id, strava_activity_id, sport, started_at, duration_sec, distance_m, avg_hr, elevation_m, name |
| `annotations` | id, user_id, **date（単日）**, **kind（`event` / `measurement`）**, title, body, **metric（enum コード。`vo2max` 等。measurement のみ）**, **value（数値。measurement のみ）**, created_at, updated_at |

**設計上の判断**

- **メモは単日で持ち、期間は持ちません**
- **メモはアクティビティに紐づけません。** 日付だけで保持し、画面上で同じ日のものを並べます（アクティビティが存在しない日にも書けるようにするため）
- 取り込むのは `bike` / `run` / `walk` に相当する Strava の種目のみとします
- **測定値は「メモの一種」として持ちます。** 専用のテーブルも専用の画面も作りません。`kind = measurement` のメモに数値を持たせるだけです。MVP では `vo2max` のみ、本リリースで `weight` を足します

  **なぜ入れるのか**: 2026年7月に腰痛で1ヶ月休んだあと、VO2max が下がっていました。**負荷が落ちたことの結果として現れる数値**であり、負荷の推移と並べると読める情報が増えます。

  **なぜ手入力なのか**: **Strava API は VO2max を持っていません**（Strava がそもそも VO2max を算出・保持していないため、連携設定の問題ではなくデータが存在しません）。取得するには Apple Watch → HealthKit → 別の連携アプリ → 別サービス、という経路が必要で、**利用者にその連鎖を要求すると想定ユーザーが激減します**。一方で VO2max は**月に1〜2回入力すれば足りる程度にしか動かない値**なので、手入力で実用上の不足がありません。

  **なぜ主役にしないのか**: VO2max を中心に据えると、別プロダクトである Cardilife と主題が重なります（→ §1）。Loadline における VO2max は、**「その日に書き残せることの一つ」**という位置づけに留めます

- **体重は、本リリースでタニタ Health Planet API から取り込みます**（`metric = weight`）。**取り込むのは体重だけ**で、体脂肪率・筋肉量などは扱いません——増やしても読み方が増えるだけで、このサービスの主題（負荷の推移と出来事）に寄与しないためです。**データモデルも画面も追加不要**で、増えるのは取り込み経路だけです——測定値メモの仕組みを先に作っておいたことが、そのまま効きます

  **サーバーセントリックであることの実例**: 端末セントリックな構成では、外部サービスの OAuth トークンを安全に置く場所がないため、この経路自体を持てません。**Loadline はサーバー側にトークンを置けるため、API から正面から取得できます。** 構成の選択が、扱えるデータ源の範囲をそのまま決めるという例です（→ §10-2）

  **これは「だめもと」の機能です。** Health Planet API が現在も新規の利用登録を受け付けているかは未確認で、比較的古い API であるため閉じている可能性があります。本企画では Google Fit REST API が 2024年5月以降 新規登録を受け付けていないと判明してデータ源の選定をやり直した経緯があるため（→ §10-2）、**着手前にまず登録可否と審査期間を確認し、通らなければこの機能は落とします。** 本リリース枠に置いているのはそのためで、**MVP も本体の価値もこの機能に依存しません**

- **LLM が生成した振り返りは、当面テーブルに保存しません**（生成のたびに返して表示するだけ）。保存して見返したいという要求が出た時点で `reviews` テーブルを足します
- **日次の指標（負荷・エンジン・疲労・余力）はテーブルに保存せず、都度計算します。** 個人利用のデータ量であれば十分な速度が出るためです。遅くなった時点でキャッシュを追加します

## 14. 画面（素案）

1. **ログイン** — 「Strava で連携」ボタンのみ
2. **チャート（メイン）** — 日次負荷の棒グラフ＋エンジン／疲労／余力の線＋メモのマーカー。期間切り替え（1ヶ月／3ヶ月／6ヶ月）。マーカーのクリックでメモを表示。**測定値メモ（VO2max）は点として重ねる**。**「この期間を振り返る」ボタンから LLM の生成文をチャートの下に表示**（生成文は必ずチャートと並べて見せます。→ 懸念点⑥）

## 15. Strava 利用規約への対応

- **レート制限**（15分あたり 200 / 1日あたり 2000）を超えない同期処理とします
- **`Powered by Strava` を表示**し、各アクティビティから Strava への遷移を設けます（利用規約上の義務）
- **他のユーザーのデータを表示する機能は設けません**（本人の記録を本人に見せるだけの構成です）
- **サービス名・ドメインに "Strava" を含めません。** サードパーティアプリの名称への使用は制限されているため、`Loadline` という名前を使います。ロゴの改変も行いません
- **連携を解除されたときの扱い**: アカウントが Strava 連携そのものであるため、ユーザーが Strava 側で認可を取り消した場合の動作を定義します。**取り込み済みのアクティビティとユーザーが書いたメモはサーバーに保存されており、Strava に依存しません**。したがって再連携すればそのまま続きから使えます（→ 懸念点②）

> **着手時に、Strava の API Agreement とブランドガイドラインの現行版を読み、本節を実際の条文に合わせて更新します。** 上記は 2026-09 時点の理解に基づく暫定の整理です。
